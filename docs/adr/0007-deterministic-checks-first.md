# ADR 0007: Deterministic checks first; corpusminder grows them

- **Status:** Accepted (operator goal, 2026-11-10).
- **Date:** 2026-11-10.
- **Deciders:** the operator.
- **Issue:** [#811](https://github.com/seanoc5/llm-swarm-runner/issues/811)
  (basic checks component).
- **Related:** [#798](https://github.com/seanoc5/llm-swarm-runner/issues/798)
  (stop-hook lint), [#801](https://github.com/seanoc5/llm-swarm-runner/issues/801)
  (corpusminder opt-in, contradictory-ending test),
  [#792](https://github.com/seanoc5/llm-swarm-runner/issues/792) (grokkability).

## Decision

Whenever a check can be a script, make it a script. This covers both the
test framework and the swarm's own processing and generation: briefs, PR
screens, coordinator replies, needs-you items.

- A deterministic check (a bash or regex lint, a jq query, a small program)
  comes first. An LLM check or eval is added on top of it only for what a
  script can't decide.
- Naive is fine. A regex that catches the real incident beats a perfect
  check that doesn't exist yet. Each check starts from a real failing
  example, kept as a fixture.
- When a rule keeps failing in prose (prompts, memories), the fix is a
  check, not more prose.
- Output that a check can verify should be generated by a script where
  possible, e.g. the closing line of a needs-you render (#801), so the
  failure can't happen at all.

## Where the work happens

This repo holds a basic checks component (#811): one simple output format
(JSON lines) and the existing lints wrapped behind it. Corpusminder is
expected to take these checks over in the coming weeks and grow them into
advanced code that augments LLM checks and evals. Keep the output format
stable so it can.

## Why

Prompt rules about reporting have failed repeatedly (#680, #792, #798: 20+
requests with no change). Scripts behave the same every run, are cheap to
run on every reply, and give the operator something measurable.
